# Android mixed-code example

This is a small existing Compose app: `MainActivity`, navigation, the home screen and the original profile screen are
hand-written. Only the displayed layout crosses the Refract boundary.

```text
MainActivity
  SettingsApp (hand-written navigation, model and binding)
    HomeScreen (hand-written)
    Hello (actual generated Compose)
    NativeComponentScreen (generated → hand-written badge)
    SettingsScreen (generated model-backed settings)
    HandWrittenSettingsScreen (native rollback)
```

`app/src/main/java/refract/generated/Hello.kt` is generated by the repository CLI from
`examples/shared/Hello.swift`. Its body matches `Fixtures/hello/Expected.kt`; its source header correctly names
`Hello.swift` rather than the fixture's `Input.swift`. `IdentifiedList.kt` and its ArkTS counterpart likewise come
from `examples/shared/IdentifiedList.swift`, the canonical identified-model list input. The hand-written
`app/src/main/java/refract/generated/SettingsScreen.kt` is actual CLI output from the canonical
`examples/shared/SettingsScreen.swift`, including its `SettingsModel` interface, `State<String>` title,
`LazyColumn` sections, TextField, Toggle and save action. The native `AppSettingsModel` implements that interface;
`HandWrittenSettingsScreen` accepts the same arguments for rollback. `SettingsApp` owns the model and binding, and
HomeScreen switches between generated and hand-written settings without a host container or runtime adapter.

No Refract library is included. The example's runtime dependencies are AndroidX and Kotlin only.
`HandWrittenSettingsScreen` remains available to demonstrate rollback. `NativeComponentScreen` demonstrates
native components inside a generated screen through the typed mapping, not an invented parallel registry.

## Build

Requirements: JDK 21, Android SDK Platform 37.2 and Build Tools 37.0.0. The wrapper uses Gradle 9.8.2. The build
uses Android Gradle Plugin 9.5.0, Kotlin/Compose plugin 2.4.21 and Compose BOM 2026.09.00; the BOM requires
compileSdk 37. `ANDROID_HOME` is the only machine-specific configuration; do not commit `local.properties`.

`gradle/wrapper/gradle-wrapper.jar` is the official Gradle 9.8.2 wrapper jar, extracted from
`gradle-9.8.2/lib/plugins/gradle-wrapper-main-9.8.2.jar` inside the verified Gradle 9.8.2 distribution (the zip
whose SHA-256 is recorded as `distributionSha256Sum` in `gradle-wrapper.properties`). Its SHA-256 is
`3b8a25775a69158b5ad2b1d17a80a88dc7b40a352a73eb27d06c612a7ce68e98`. If the wrapper is regenerated with
`gradle wrapper`, restore that exact jar rather than a jar from a different Gradle version: an older jar's
`Install.unzip` references `org.gradle.internal.file.PathTraversalChecker`, which is not bundled in older jars
and crashes the bootstrap with `NoClassDefFoundError` on a cold distribution cache.

AGP 9 supplies built-in Kotlin support. Do not apply `org.jetbrains.kotlin.android`; use
`KotlinAndroidProjectExtension.compilerOptions` to retain JVM 17 bytecode while building with JDK 21.

```sh
export ANDROID_HOME=/path/to/android-sdk
export JAVA_HOME=/path/to/jdk21
cd examples/android
./gradlew :app:assembleDebug
```

The APK is produced at `app/build/outputs/apk/debug/app-debug.apk`. The standard debug variant is signed with the
local debug key by the Android plugin; no application signing key is committed. There is no emulator or device
performance result for this example.

To compile only the Kotlin and its resources, run `./gradlew :app:compileDebugKotlin`.

## CI compile gate

`.github/workflows/ci.yml` runs an `android-compile` job on every pull request and on every push to `main`. The job
builds the `refract` CLI, runs `scripts/check_examples.py` to regenerate this example and reject stale committed
output, then invokes `./gradlew --no-daemon :app:compileDebugKotlin` against a pinned JDK 21 + Android SDK
(platform `android-37.2`, build tools `37.0.0`). The compile is byte-equivalent to the local command above; the
job never edits the generated files and never accepts a Kotlin compiler failure. It includes no emulator, device or
performance measurement. Its additional fixture JVM tests run Compose on Robolectric, also not a device. See
`../../docs/ci.md` for the toolchain pins and cache layout.

The same job also compiles the canonical fixture corpus. `fixture-compile-manifest.txt` (next to this README)
lists the fixtures to compile (one per line, names are directories under `Fixtures/`).
`scripts/check_fixture_compilation.py` regenerates each listed fixture through the actual CLI, diffs the output
against the committed `Expected.kt`, and stages the Kotlin plus the fixture's `values/strings.xml` under
`fixtures/src/main/`. The Gradle module at `fixtures/` is an Android library whose
`namespace = "refract.generated"` matches the package declared by every fixture's `Expected.kt`, so the generated
`R` class is `refract.generated.R`. The job then runs `./gradlew --no-daemon :fixtures:compileDebugKotlin`.
The staged files are `.gitignored` and produced on every CI run; they are never committed. To add a fixture to
the compile set, append its directory name to `fixture-compile-manifest.txt`. There is no skip list: any new
compile failure must be fixed in the same PR.

To run the fixture gate locally, from the repository root:

```sh
swift build
python3 scripts/check_fixture_compilation.py
cd examples/android
./gradlew :fixtures:compileDebugKotlin
```

### Native animation lifecycle tests

The app-owned `NativeSaveConfirmation` demonstrates a typed visibility/identity boundary. Its implementation uses
`AnimatedVisibility`; `MotionDurationScale` follows the system animation scale, and `key(identity)` gives replacement
content a new native transition. It has no Refract runtime dependency. Its optional observer is an application
`CompositionLocal`, not an extra generated argument; the tests provide it around the exact CLI-generated caller.
The native contract, iOS implementation and HarmonyOS limits are documented in `../../docs/interop.md`.

The fixture JVM tests verify ordinary transition running/idle states, disposal on identity replacement during an
in-flight transition, exit removal, zero-scale enter/exit and removal from composition. The fixture module includes
that app-owned implementation in its Android source set so the generated import is a real compiler dependency.
Run the tests after `swift build` and `scripts/check_fixture_compilation.py`:

```sh
cd examples/android
./gradlew :fixtures:testDebugUnitTest
```

Robolectric 4.16 executes Compose with a test-provided `MotionDurationScale` and deterministic clock. This is a local
JVM behavior check, not a physical system-settings test, device/emulator run or timing benchmark. The Gradle cache key
includes this module's build script so changes to its dependency pins invalidate CI caches.

## Regenerate and check

From the repository root, build the CLI, generate both native outputs and compare them with the reviewed canonical
fixture:

```sh
swift build
python3 scripts/check_examples.py
.build/debug/refract generate \
  --input examples/shared/Hello.swift \
  --input examples/shared/NativeComponentScreen.swift \
  --input examples/shared/IdentifiedList.swift \
  --input examples/shared/SettingsScreen.swift \
  --mapping examples/refract.json \
  --android-out examples/android/app/src/main/java/refract/generated \
  --harmony-out examples/harmony/entry/src/main/ets/generated
diff <(tail -n +3 Fixtures/hello/Expected.kt) <(tail -n +3 examples/android/app/src/main/java/refract/generated/Hello.kt)
diff <(tail -n +3 Fixtures/hello/Expected.ets) <(tail -n +3 examples/harmony/entry/src/main/ets/generated/Hello.ets)
```

Changing the shared Swift input regenerates both platforms in place; do not edit either output independently.

## Adopt or roll back

`SettingsApp.kt` switches between `SettingsScreen` and `HandWrittenSettingsScreen` with the same model, binding and
callback. `HomeScreen` owns the toggle; navigation, state and rollback remain native. The full model-backed adoption
and rollback procedure is in `../../docs/adoption.md`.
