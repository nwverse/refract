# Android mixed-code example

This is a small existing Compose app: `MainActivity`, navigation, the home screen and the original profile screen are
hand-written. Only the displayed layout crosses the Refract boundary.

```text
MainActivity
  SettingsApp (hand-written navigation, model and binding)
    HomeScreen (hand-written)
    Hello (actual generated Compose)
    NativeComponentScreen (generated → hand-written badge)
    SettingsScreen (generated model-backed settings)
    HandWrittenSettingsScreen (native rollback)
```

`app/refract/generated/screens/Hello.kt` is generated by the repository CLI from
`examples/shared/Hello.swift`. Its body matches `Fixtures/hello/Expected.kt`; its source header correctly names
`Hello.swift` rather than the fixture's `Input.swift`. `IdentifiedList.kt` and its ArkTS counterpart likewise come
from `examples/shared/IdentifiedList.swift`, the canonical identified-model list input. The hand-written
`app/refract/generated/screens/SettingsScreen.kt` is actual CLI output from the canonical
`examples/shared/SettingsScreen.swift`, including its `SettingsModel` interface, `State<String>` title,
`LazyColumn` sections, TextField, Toggle and save action. The native `AppSettingsModel` implements that interface;
`HandWrittenSettingsScreen` accepts the same arguments for rollback. `SettingsApp` owns the model and binding, and
HomeScreen switches between generated and hand-written settings without a host container or runtime adapter.

No Refract library is included. The example's runtime dependencies are AndroidX and Kotlin only.
`HandWrittenSettingsScreen` remains available to demonstrate rollback. `NativeComponentScreen` demonstrates
native components inside a generated screen through the typed mapping, not an invented parallel registry.

## Build

Requirements: JDK 21, Android SDK Platform 37.2 and Build Tools 37.0.0. The wrapper uses Gradle 9.8.2. The build
uses Android Gradle Plugin 9.5.0, Kotlin/Compose plugin 2.4.21 and Compose BOM 2026.09.00; the BOM requires
compileSdk 37. Native JVM Compose tests additionally pin Robolectric 4.18 and Android API 35 for their test runtime.
`ANDROID_HOME` is the only machine-specific configuration; do not commit `local.properties`.

`gradle/wrapper/gradle-wrapper.jar` is the official Gradle 9.8.2 wrapper jar, extracted from
`gradle-9.8.2/lib/plugins/gradle-wrapper-main-9.8.2.jar` inside the verified Gradle 9.8.2 distribution (the zip
whose SHA-256 is recorded as `distributionSha256Sum` in `gradle-wrapper.properties`). Its SHA-256 is
`3b8a25775a69158b5ad2b1d17a80a88dc7b40a352a73eb27d06c612a7ce68e98`. If the wrapper is regenerated with
`gradle wrapper`, restore that exact jar rather than a jar from a different Gradle version: an older jar's
`Install.unzip` references `org.gradle.internal.file.PathTraversalChecker`, which is not bundled in older jars
and crashes the bootstrap with `NoClassDefFoundError` on a cold distribution cache.

AGP 9 supplies built-in Kotlin support. Do not apply `org.jetbrains.kotlin.android`; use
`KotlinAndroidProjectExtension.compilerOptions` to retain JVM 17 bytecode while building with JDK 21.

```sh
export ANDROID_HOME=/path/to/android-sdk
export JAVA_HOME=/path/to/jdk21
swift build --package-path ../..
export REFRACT_CLI_PATH="$PWD/../../.build/debug/refract"
export REFRACT_REQUIRED_VERSION="$($REFRACT_CLI_PATH --version)"
./gradlew -p examples/android :app:assembleDebug
./gradlew -p examples/android :app:checkDebugRefract

```

The APK is produced at `app/build/outputs/apk/debug/app-debug.apk`. The standard debug variant is signed with the
local debug key by the Android plugin; no application signing key is committed. There is no emulator or device
performance result for this example.

To compile only the Kotlin and its resources, run `./gradlew :app:compileDebugKotlin`.

## Native JVM Compose rendering and interaction tests

The `:app` `src/test` source set calls the actual CLI-generated `refract.generated.SettingsScreen` in the real
application resource package, not a copied or hand-written replacement. This matters because a separate Android
library's local test APK does not contain a dependent app's resource table: numeric `R` references can otherwise
resolve to unrelated strings. From the repository root, first prove the generated file is current, then run the JVM
tests:

```sh
swift build
python3 scripts/check_examples.py
cd examples/android
./gradlew :app:testDebugUnitTest
```

The tests use Compose UI testing on Robolectric with native graphics. They exercise the visible rows, the notification
label's relationship to the native Switch, Switch role/checked/click semantics, binding updates, text input, model
updates and the save callback. The separate `generatedRowsExposeTheirRelationshipWithoutInventedSemantics` test
observes the label and control as separate semantics nodes; the test does not add a row merger or accessibility
behavior that the generator did not emit.

Light and dark captures and the dark-mode semantics tree are written to
`app/build/reports/native-jvm-compose/`. **These are Native JVM Compose captures, not device or emulator
screenshots.** They are not visual-parity or performance measurements and must be visually inspected. CI publishes
them and the JUnit HTML reports as `native-jvm-compose-settings`. Tests and their dependencies are confined to the
application's test source set and add no runtime library to the example APK, generated code or consuming apps.
Large-text behavior is tracked separately by the accessibility workstream and is not claimed by this check.

## CI compile gate

`.github/workflows/ci.yml` runs an `android-compile` job on every pull request and on every push to `main`. The job
builds the `refract` CLI, runs `scripts/check_examples.py` to regenerate this example and reject stale committed
output, then invokes `./gradlew --no-daemon :app:compileDebugKotlin` against a pinned JDK 21 + Android SDK
(platform `android-37.2`, build tools `37.0.0`). The compile is byte-equivalent to the local command above; the
job never edits the generated files and never accepts a Kotlin compiler failure. It includes no emulator, device or
performance measurement. Its additional fixture JVM tests run Compose on Robolectric, also not a device. See
`../../docs/ci.md` for the toolchain pins and cache layout.

The same job also compiles the canonical fixture corpus. `fixture-compile-manifest.txt` (next to this README)
lists the fixtures to compile (one per line, names are directories under `Fixtures/`).
`scripts/check_fixture_compilation.py` regenerates each listed fixture through the actual CLI, diffs the output
against the committed `Expected.kt`, and stages the Kotlin plus the fixture's `values/strings.xml` under
`fixtures/src/main/`. The Gradle module at `fixtures/` is an Android library whose
`namespace = "refract.generated"` matches the package declared by every fixture's `Expected.kt`, so the generated
`R` class is `refract.generated.R`. The job then runs `./gradlew --no-daemon :fixtures:compileDebugKotlin`.
The staged files are `.gitignored` and produced on every CI run; they are never committed. To add a fixture to
the compile set, append its directory name to `fixture-compile-manifest.txt`. There is no skip list: any new
compile failure must be fixed in the same PR.

To run the fixture gate locally, from the repository root:

```sh
swift build
python3 scripts/check_fixture_compilation.py
cd examples/android
./gradlew :fixtures:compileDebugKotlin
```

### Theme interaction and dynamic-type Native JVM tests

`theme-interaction-states` supplies one generated settings component, an app-owned state resolver and light/night
resources. `ThemedSettingsAction` observes one actual `MutableInteractionSource` and passes its Boolean pressed and
focused values into the generated component. The independent `theme-fixture` module compiles the exact golden Kotlin
with those application resources, and CI includes it in the Android compile gate:

```sh
./gradlew :theme-fixture:compileDebugKotlin
```

The fixture test source set compiles that same generated component again with Robolectric and runs
`ThemeInteractionTest`. It verifies actual press/focus/disabled precedence, light-versus-night rendered pixels and
default-versus-2x-fontScale text bounds. Run the canonical staging step first, then:

```sh
python3 scripts/check_fixture_compilation.py
cd examples/android
./gradlew :fixtures:testDebugUnitTest --tests com.example.refract.theme.ThemeInteractionTest
```

The captures and measured bounds are written to `fixtures/build/reports/native-jvm-compose/` and uploaded as
`native-jvm-compose-theme` by CI. **These are Native JVM Compose results, not emulator/device screenshots, physical
screen-reader checks or performance measurements.** The resolver is application code, not a Refract runtime or an
automatic interaction-state discovery mechanism. iOS and ArkUI compilation/rendering are separate tool checks.

### Native animation lifecycle tests

The app-owned `NativeSaveConfirmation` demonstrates a typed visibility/identity boundary. Its implementation uses
`AnimatedVisibility`; `MotionDurationScale` follows the system animation scale, and `key(identity)` gives replacement
content a new native transition. It has no Refract runtime dependency. Its optional observer is an application
`CompositionLocal`, not an extra generated argument; the tests provide it around the exact CLI-generated caller.
The native contract, iOS implementation and HarmonyOS limits are documented in `../../docs/interop.md`.

The fixture JVM tests verify the generated call's final stable state, disposal on identity replacement, exit removal,
zero-scale enter/exit and removal from composition. The fixture module includes that app-owned implementation in its
Android source set so the generated import is a real compiler dependency. Run the tests after `swift build` and
`scripts/check_fixture_compilation.py`:

```sh
cd examples/android
./gradlew :fixtures:testDebugUnitTest
```

The separate `NativeSelectionEmphasis` fixture follows #159 without duplicating its visibility component. It uses
an app-owned `Animatable` for a stateful value transition: target changes cancel and resume from the current
progress, identity replacement disposes the old remembered animation, and zero `MotionDurationScale` snaps without
intermediate progress. Six additional JVM tests exercise the unchanged CLI-generated caller, reversal, identity,
reduced motion and disposal. `Fixtures/interop-native-state-transition/` supplies the independent dual-backend
golden and is part of the real Kotlin fixture compile gate.

Robolectric 4.18 executes Compose with a test-provided `MotionDurationScale` and deterministic clock. This is a local
JVM behavior check, not a physical reduced-motion system-settings test, device/emulator run or timing benchmark. The
Gradle cache key includes this module's build script so changes to its dependency pins invalidate CI caches. The
fixture module resolves the same pinned Android-all runtime as the app tests and runs Robolectric offline.

### Synthetic document preview lifecycle tests

`interop-document-preview` exercises typed document metadata, exhaustive loading/missing/unsupported/cancelled/closed
states and a checked native close action on both generated backends. Its app-owned native implementation is confined
to the fixture module's `src/native` source set. `SyntheticDocumentController` reads only the committed synthetic
plain-text resource, checks its bytes and owns cancellation, decoded-content cleanup and close. No URI permission or
decoder is supplied by Refract, and no private document, WebView or remote fetch is involved. PDF/image metadata is
not a claim of a working renderer. See `../../docs/document-preview.md` for the ownership and verification limits.

The same staging and `:fixtures:testDebugUnitTest` commands above compile the real CLI-generated Kotlin and run three
Native JVM Compose document tests: ready/close/disposal, missing/unsupported and cancellation with no stale ready
result. These are source and Native JVM results only, not emulator, device, iOS or HarmonyOS verification.

### Incremental search model tests

`list-paged-search` compiles the actual dual-backend fixture output and the app-owned
`IncrementalSearchResultsModel` together. The model is application code, not generated output or a Refract runtime.
Its JUnit tests run on the host JVM with a scripted in-memory transport and cover append/replacement identity,
duplicate/out-of-order response rejection, cancellation, loading/empty state and error retry. Run them with the same
fixture staging step followed by:

```sh
./gradlew :fixtures:testDebugUnitTest --tests com.example.refract.search.IncrementalSearchResultsModelTest
```

This is native model JVM evidence only. It performs no network request, renders no UI and supplies no emulator,
device, ArkTS compiler, runtime observation or performance evidence. A HarmonyOS implementation must provide the
corresponding app-owned data-source notifications and lifecycle cancellation described in `docs/state-and-models.md`.

### Typed projection tests

`list-typed-projection` compiles the actual generated Compose pure projection. Its Native JVM test covers empty input,
finite category filtering, `.all` reset, descending Int rank, ascending Int id ties and original item instance identity:

```sh
./gradlew :fixtures:testDebugUnitTest --tests com.example.refract.projection.CatalogProjectionTest
```

The generated list retains original item ids. The reviewed ArkUI output exports the pure function and consumes the
app-owned projected `BasicDataSource`; it has no runtime mirror or synchronization adapter. ArkTS, iOS and device
compilation are not claimed by this host-JVM test.

## Opt-in Gradle generation

The repository's `tools/gradle/` build supplies the `dev.refract.generator` plugin. `app/build.gradle.kts` opts in
and declares the four shared Swift inputs as the `screens` group, using the shared mapping and both resource
catalogs. `REFRACT_CLI_PATH` supplies a version-matched CLI and `REFRACT_REQUIRED_VERSION` pins its exact
`refract --version` output before generation or publication. The existing debug/release source-group roots remain the
reviewed production outputs. To bind debug, internal and release to separate output roots, publish
them explicitly and check both native backends, see `../../docs/generation-configurations.md`. An application may instead set `refract.executable`; the plugin never runs an implicit
Swift build. There is no Refract runtime dependency or application start-up hook.

`:app:generateDebugRefract` generates the group below the variant's build-owned `generated/refract/` directory.
AGP exposes the compiled files below `build/generated/java/<generation-task>/`. Android's per-variant
`addGeneratedSourceDirectory` connects these task outputs to `compileDebugKotlin`, so compilation depends on
generation without eagerly realizing tasks. `:app:compileDebugKotlin` is the normal consumer entry point. Run it
twice: the second build reports the generation task `UP-TO-DATE`. Changing a Swift input, mapping, declared
resource catalog or CLI executable invalidates the relevant group. `:app:clean :app:compileDebugKotlin` regenerates
and compiles from an empty build directory.

Reviewed generated Kotlin lives in `app/refract/generated/<group>/`, not in an ordinary Android source root. This
keeps the compiled copy unambiguous: the build always uses its fresh generated copy. `:app:checkDebugRefract`
invokes the CLI's read-only `check` with all four Swift inputs, the shared mapping and the canonical Kotlin/ArkTS
output directories. Missing, stale or extra outputs fail without modifying a source file. `checkRefract` covers
every Android variant.

The plugin supports Android applications and the example's documented Gradle/AGP versions. It is a repository-local
composite build, not a claim that a versioned plugin has been published to a public plugin repository. The
`tools/gradle/` functional tests create a small real Android application and run the actual CLI to verify native
Kotlin compilation, incremental generation, missing-tool diagnostics, invalid-input safety and stale checks.

## Regenerate and check

From the repository root, build the CLI, generate both native outputs and compare them with the reviewed canonical
fixture:

```sh
swift build
.build/debug/refract check \
  --input examples/shared/Hello.swift \
  --input examples/shared/NativeComponentScreen.swift \
  --input examples/shared/IdentifiedList.swift \
  --input examples/shared/SettingsScreen.swift \
  --mapping examples/refract.json \
  --android-out examples/android/app/refract/generated/screens \
  --harmony-out examples/harmony/entry/src/main/ets/generated
python3 scripts/check_examples.py
.build/debug/refract generate \
  --input examples/shared/Hello.swift \
  --input examples/shared/NativeComponentScreen.swift \
  --input examples/shared/IdentifiedList.swift \
  --input examples/shared/SettingsScreen.swift \
  --mapping examples/refract.json \
  --android-out examples/android/app/refract/generated/screens \
  --harmony-out examples/harmony/entry/src/main/ets/generated
diff <(tail -n +3 Fixtures/hello/Expected.kt) <(tail -n +3 examples/android/app/refract/generated/screens/Hello.kt)
diff <(tail -n +3 Fixtures/hello/Expected.ets) <(tail -n +3 examples/harmony/entry/src/main/ets/generated/Hello.ets)
```

Changing the shared Swift input regenerates both platforms in place; do not edit either output independently.
`refract check` performs the same generation in memory and fails on missing, stale or extra committed Kotlin/ArkTS
without writing files. Supply the complete input set for both output directories.

## Adopt or roll back

`SettingsApp.kt` switches between `SettingsScreen` and `HandWrittenSettingsScreen` with the same model, binding and
callback. `HomeScreen` owns the toggle; navigation, state and rollback remain native. The full model-backed adoption
and rollback procedure is in `../../docs/adoption.md`.
