# Android generated-vs-native benchmark harness

The app module contains a performance-shaped Compose settings screen and a hand-written reference of the same UI.
The `Generated` variant is the actual `SettingsScreen` generated by the CLI from `SettingsScreen.swift`;
`GeneratedSettingRow` is its generated child composable and remains directly callable by the row microbenchmark.
`ReferenceSettingsScreen.kt` is unchanged hand-written code. There is no benchmark runtime library in either
compared screen.

`report.py` pairs `Generated` and `Reference` results from the benchmark integration, reports raw samples and
p50/p99, rejects missing pairs, non-finite values and different build/device contexts, and returns nonzero for a
latency regression beyond 5% AND 0.1 ms. The absolute gate is time-based; memory and frame-overrun metrics are
reported separately, not compared with a millisecond threshold. Microbenchmark aggregate medians are diagnostic,
not a fictitious p99 sample.

## Current integration status

- The app compiles for release with the pinned Compose BOM, material3 `Switch`, stable lazy-list keys/content type,
  and narrow `State<T>` reads.
- `report_test.py` verifies parsing, pairing, quantiles, environment checks and threshold behavior.
- Both real setting-row microbenchmark variants pass on an AOSP API 35 x86_64 emulator and produce actual AndroidX
  JSON with 50 timing samples and 5 allocation samples per variant. The parser accepts this real format, including
  top-level context and `EMULATOR_` method prefixes. The real-row comparison (generated p50 100.541ms, reference
  149.006ms; generated p99 170.044ms, reference 615.354ms) passed the emulator gate. Earlier duplicate toy-row
  measurements used different content and are not comparable baselines; these results are not physical-device
  evidence or a generator-wide performance guarantee.
- Macrobenchmark/Microbenchmark instrumentation is present. On the available software-only emulator, startup
  frame completion can exceed the platform's fixed activity-launch deadline (`lastFrameNs=null`) or the system can
  become unresponsive. No successful macrobenchmark result is claimed from that environment. The runner fails
  rather than converting an incomplete trace into a passing report.
- The app disables shrinking to preserve both variant function boundaries, uses debug signing for local
  instrumentation and has a `profileable` release manifest. These are harness choices, not production performance
  claims.

## Prerequisites

Use JDK 17+ (JDK 21 is supported by the pinned AGP) and an Android SDK with API 36/build-tools. Set `ANDROID_HOME`
and `GRADLE_USER_HOME` for your machine, not in repository files. Dependency versions are pinned in
`app/build.gradle.kts`.

```sh
# No device needed:
python3 -I bench/android/report_test.py
python3 -I bench/android/evidence_test.py
python3 -I bench/android/runner_test.py
bench/android/gradlew -p bench/android :app:assembleRelease :benchmark:assembleRelease

# Regenerate and compile, or fail if any committed generated output is stale:
JAVA_HOME=/path/to/jdk bench/android/generate-and-compile.sh
JAVA_HOME=/path/to/jdk bench/android/generate-and-compile.sh --check

# One already-booted, stable emulator with mounted, writable external storage:
bench/android/run-emulator.sh bench/android/results/emulator-01
```

`run-emulator.sh` requires a committed source tree so that the revision names every generator and harness input.
`probe_target.py` only selects an attached target and reads bounded boot/package/mount/SurfaceFlinger/storage
properties. It does not create, boot, stop, root or reboot an emulator, and it rejects an offline, incomplete or
storage-unready target before Gradle instrumentation starts. Its only target write is the documented output-directory
writability test; the runner separately disables animations. The JSON records model, device, OS/build, ABI, rendering
properties, compilation mode, macro iteration count and the exact Git revision. Gradle passes that same revision through
AndroidX `output.payload.refract.sourceRevision`, and both collector and report require it to match the preserved
AndroidX `context.payload`. The runner also records that HEAD matched and the worktree remained clean after
generation, compilation and measurement. The environment is copied into `raw/environment.json` and protected by the
same evidence checksum manifest; a missing, mismatched or changed environment blocks the report. Local run metadata
retains the selected target serial and Gradle receives that exact serial through `android.test.devices`, so a second
attached target cannot redirect or duplicate the measurement. Run directories and serial-bearing reports are not
committed. A dirty source tree is rejected. Any old `additional-output` directory is moved intact into the new run
directory before instrumentation so historical JSON/traces cannot be mistaken for this run's evidence.

`run-emulator.sh` first checks that the real CLI regenerates the exact committed Kotlin and fixture ArkTS without
installing changes, then compiles the release artifacts. After instrumentation it preserves every AndroidX JSON and
`.perfetto-trace` file with SHA-256 checksums in a new per-run directory. `report.py --require-macro` requires both
variants of startup, scroll and state update, at least ten iterations, raw `timeToInitialDisplayMs` startup samples,
`frameDurationCpuMs` frame samples, one `MemoryUsageMetric(Mode.Last)` memory sample per declared scroll/state-update
iteration (for example `memoryRssAnonLastKb`), matching metrics and a distinct indexed Perfetto trace for every declared
iteration. Startup samples must match the iteration count; frame runs contain per-frame samples across iterations and
are not mislabelled as iteration samples. Each macro record's AndroidX `profilerOutputs` must
reference a retained trace with the matching variant/scenario; unreferenced or ambiguous traces fail closed. Missing
pairs, JSON, traces, mismatched checksums or incomplete traces fail rather than becoming a partial PASS. AOSP images
without Google services need the same startup/rendering stability checks; slow first frames are not accepted as
passing startup measurements. The existing frame deadline and 5% AND 0.1 ms latency gate are unchanged.

The Gradle wrapper bootstrap and distribution have pinned versions. On a new machine the wrapper downloads its
distribution from the public Gradle service; no local proxy or internal mirror is configured in this project.

## Adding real generated benchmarks

After `swift build`, run `JAVA_HOME=/path/to/jdk bench/android/generate-and-compile.sh`. It regenerates both native
outputs into the ignored `tmp/benchmark-generated/` directory, installs the exact Kotlin as
`screen/src/main/java/dev/refract/bench/SettingsScreen.kt`, and compiles the shared library, app and
self-instrumented test release artifacts without starting an emulator. The `:screen` Android library owns the
real generated UI, unchanged hand-written reference and model boundary; app and test modules depend on that
library rather than recompiling generated source under incompatible resource namespaces. `SettingsModel.kt`
retains only the hand-written `BenchmarkSettingsModel` implementation; the CLI owns the `SettingsModel`
interface and `SettingRow` declarations. `refract.json` and the Android/HarmonyOS catalogs declare the same
`settings.item` resource. Diff both outputs and do not edit the Kotlin/ArkTS independently. ArkTS generation is
not ArkTS compilation.

The generated screen and hand-written reference now share the title typography, list/row measurement tags,
stable keys and `setting` row type, independent row boundary, width/weight/centering, Switch accessibility and
per-row `remember(model, row.id)` callback. `Fixtures/benchmark-settings` uses the identical Swift source, and its
Kotlin/ArkTS goldens are actual CLI output. `generate-and-compile.sh` verifies the exact installed Kotlin by
regenerating it and running release builds. These are structural and compilation checks, not performance proof.
A compile success alone cannot satisfy goal 2, and emulator-only measurements cannot close the
physical-device evidence gap. The current environment has no `/dev/kvm` or attached physical device. A clean Google
APIs API 35 attempt also failed to provide a writable benchmark output volume and stable package/mount services;
do not repeatedly restart it or substitute toy measurements. A named target with responsive package/graphics
services, writable `/sdcard/Android/media` and complete paired JSON/Perfetto traces is required for macro evidence.
