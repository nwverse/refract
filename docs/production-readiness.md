# Production-readiness evidence

This is the evidence index for the five goals and the roadmap. It does not redefine either one. **Refract is in early
development and is not production-ready.** An open issue records a gate and its owner, not evidence that the gate has
passed. Issue counts, generated-file counts and source inspection are not production-validation results.

## Audited baseline

The initial audit covers main revision `397315e`, merged by [PR #149](https://github.com/nwverse/refract/pull/149) on
2026-11-17. Its [main CI run](https://github.com/nwverse/refract/actions/runs/43997732490) passed. That run verifies
the generator, repository checks and generated Android Kotlin; it does not build an iOS application, compile ArkTS or
measure a device. Repository links below describe current main; linked PRs, CI runs and retained reports identify the
merged evidence on which the assessment is based.

## Evidence levels

These levels are cumulative only for the **same source revision, generated artifact and execution target**.

| Level | Required evidence | What it does not prove |
| --- | --- | --- |
| Specified | A reviewed contract in `docs/` | Implementation or native-toolchain acceptance |
| Generated | Actual CLI output matches a reviewed dual-backend golden or committed example | Native compilation, rendering or performance |
| Compiled | The platform's native compiler builds the exact generated source and its native caller/model | UI behavior, visual correctness or performance |
| Rendered | The real application/component runs, behavior is exercised and captures are inspected; the host is named | Device performance; a JVM or simulator result is not a device result |
| Measured | Paired raw samples/traces, environment metadata and a fail-closed report compare generated and equivalent native code | Other source shapes, platforms, targets or a physical-device result when the target was an emulator/simulator |
| Unverified | No merged artifact establishes the requested level | No positive claim may be inferred |

A passing test suite can support one of these levels only when its command and artifact actually exercise that level.
The [fixture manifest](../Fixtures/Corpus.json) also keeps pending cases distinct from ready golden cases.

## Adoption support and deprecation policy

### What is supported now

There is **no production-supported platform or support service-level commitment** at this revision. Experimental
evaluation is limited to source accepted by the [subset contract](subset.md), with the strongest current path being the
Android settings-shaped example. That path still requires the consumer to validate its own application behavior and
performance. iOS and HarmonyOS examples must not be described as verified apps until their respective evidence lands.

An evaluation must:

1. Pin the generator source/tool versions and all native dependencies; do not treat a moving main revision as a
   supported release.
2. Generate and review both native outputs from the same Swift source, then compile and test them with the consumer's
   actual native toolchains. A golden match on another revision is not a compatibility result.
3. Supply the application's own models, resources, design-system implementations and typed native components. Keep
   navigation, lifecycle and business logic in app-owned native code unless the relevant merged contract explicitly
   supports them.
4. Keep an equivalent native call path and test rollback. Reject unsupported constructs at generation time rather than
   copying a fixture, deleting an accessibility/performance hook or hand-editing output still marked generated.
5. Measure the actual generated screen against an equivalent native implementation on the intended targets. No project
   maintainer approval, production-readiness endorsement or performance guarantee is implied by this evaluation.

### Compatibility and deprecation

`schemaVersion: 1`, stable diagnostic codes and reviewed generated signatures are current contracts, not a published
long-term compatibility guarantee. There is no supported-release deprecation window, long-term-support branch or
automatic migration promise yet. Consumers should expect to pin a revision, regenerate in a clean checkout, review API
and native-output changes, and repeat their native verification before updating.

Issue #161 owns the supported-mapping compatibility and failure-policy audit; #154 owns versioned local release
artifacts. A future supported release must publish its compatibility/deprecation window and migration procedure before
claiming one. Until then, the safe rollback is to retain the previous pinned generator and generated outputs, or take
ownership of generated files as described in the [adoption guide](adoption.md). No compatibility window is inferred
from issue closure or CI success.

## Maintaining this index

- Any PR that adds, removes or changes platform evidence updates the relevant cell, evidence link and owner in the same
  PR. The owner of that evidence is responsible for the update; this index does not transfer implementation ownership.
- Record the source revision, exact command or workflow, native toolchain and execution target. Link retained raw
  reports where measurements are claimed; never replace them with only a summary percentage.
- Name JVM, simulator and emulator evidence explicitly. Do not aggregate different targets into a device claim or use
  CI success on one platform as evidence for another.
- Keep blockers and unsupported constructs visible. Closing a tracking issue requires its own acceptance evidence; it
  does not automatically make every dependent production gate pass.
- Do not edit `docs/SUPER_RULES.md` or `docs/GOALS.md` to resolve an evidence gap. Conflicts are resolved by narrowing
  the claim and recording the missing evidence.
