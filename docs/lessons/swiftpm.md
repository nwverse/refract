# SwiftPM integration lessons

- **Forward executable discovery into the build command.** `REFRACT_EXECUTABLE` may be visible while the plugin creates commands but absent when the sandbox executes one. Resolve the executable in the plugin and pass its absolute path in `Command.buildCommand(environment:)`; an invalid override must fail, not silently fall back.
- **Do not declare Kotlin or ArkTS as outputs of an iOS host build command.** SwiftPM classifies build-command outputs by extension and can treat them as target resources. Stage those files under the plugin work directory through tool arguments, and declare a comment-only Swift file to order host compilation after generation/checking.
- **A successful command exit is not an ordering guarantee.** Without an output that the target compiles, host compilation can start independently of generation. The generated anchor has no declarations or runtime behavior and is not a replacement Swift implementation.
- **Missing inputs can fail before the tool runs.** SwiftPM's planner rejects a declared read-only input that does not exist, so a missing committed output may not reach the tool's friendly diagnostic. Test both this fail-closed behavior and the read-only stale-output check rather than requiring one exact error layer.
- **Separate dependency files from generator inputs.** Mapping catalogs and extra resources need `inputFiles` tracking, but must not be forwarded as CLI `--input` arguments or the parser will try to parse XML/JSON as Swift.
- **Keep publication separate from checking.** Build-tool plugins cannot write the package directory. Only an explicit command with `writeToPackageDirectory` permission may publish committed output; `--check` must remain read-only even if its product declares that permission for the generation operation.
- **Test portable consumer layouts without machine paths.** A relative local package dependency resolves from the consuming package, not necessarily from an enclosing repository checkout. The integration test copies the consumer to an empty temporary workspace and supplies a sibling link to the exact generator source. No local path belongs in the committed fixture.
- **Do not call a Linux syntax stub SwiftUI verification.** If a test target supplies just enough declarations for `import SwiftUI`, it proves only host build ordering. Real SwiftUI/iOS compilation and visual evidence require the native app on macOS and remain separate.
