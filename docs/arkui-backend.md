# ArkUI backend

This document specifies how `RefractArkUI` lowers the platform-neutral IR to ArkTS. The accepted Swift constructs and
their diagnostics are owned by `docs/subset.md`; this page records the platform-specific output and the reasons for
its restrictions. The backend never interprets a view tree at run time and never imports a Refract library.

## Output contract

- Each input file produces one `.ets` file, with a header naming the source and saying `Generated by Refract; do not
  edit.` Byte-identical input, mapping and generator version must produce byte-identical output. Two spaces are used
  for indentation; declarations, imports and properties have a fixed order.
- A Swift `View` becomes an exported `@ComponentV2 struct` with `build()`. There is no `@Entry`: navigation and the
  app's existing page own entry points. Public input properties use `@Param`; local mutable values use `@Local`.
  `@Event` callbacks express parent-owned actions. Component declarations use V2 consistently, rather than mixing
  V1 `@State`/`@Link` observation with V2 components.
- When a generated child View, model, item or enum is declared in another explicit input, the generated file imports
  that declaration from its sibling output (`import { ChildRow } from './ChildRow';`). Imports are grouped by source
  file, with paths and symbols sorted; a model's collection item type is imported as well. Each declaration is emitted
  once, in its owning input's output. These are ordinary static imports, not a runtime symbol registry.
- ArkTS is emitted with explicit declared property types. `any`, untyped object literals, structural interface
  matching and implicit globals are not generated. The mapping contract supplies the types of design-system and
  native component arguments. The compiler, rather than textual token substitution, resolves platform values.

The v0 target is API 12 or newer, where state management V2 is available. V1 output for older API levels is not
silently substituted. `@ObservedV2`/`@Trace` are model-implementation concerns; the component generator consumes
the declared model interface and must not add them to an app's model by assumption.

## Views and layout

| SwiftUI | ArkUI output | Contract |
| --- | --- | --- |
| `VStack` | `Column` | Explicit alignment and finite spacing; no extra wrapper. |
| `HStack` | `Row` | Same alignment and spacing semantics as the subset contract. |
| `ZStack` | `Stack` | Declared content alignment; children retain source order. |
| `ScrollView` | `Scroll` with one direct container | `.vertical()` or `.horizontal()`; `Scroll` itself has exactly one child. |
| `Text` | `Text` | Typed text expression and supported text attributes. |
| `Image` | `Image` | Resolved app resource; never an unvalidated dynamic resource lookup. |
| `Button` | `Button` with label child | `.onClick` is a typed callback, not stringified source. |
| `Toggle` | `Toggle` | Typed boolean value and change action; binding semantics come from #5. |
| `TextField` | `TextInput` | Text and change callback use the binding contract. |
| App/native component | The declared ArkUI name | Arguments are resolved and checked by `RefractMapping`/#7. |
| `if`/`else` | `if`/`else` inside `build()` | No eager evaluation of inactive branches. |
| `ForEach` with identity | `List` + `LazyForEach` + `ListItem` | Stable identity and lazy rendering; see below. |

Unsupported modifiers and layout combinations are build-time diagnostics with the construct, reason and alternative.
In particular, a lazy list is not moved into `Column` or `ForEach`, which would eagerly instantiate every item. A
scrollable list must have one `Scroll` owner. Spacer and scrolling-axis behavior require explicit support in the
subset rather than an approximate generated layout.

## Modifiers

Modifiers become chained ArkUI attribute methods after the view's closing parenthesis or child block. Their source
order is retained where ArkUI attributes are order-sensitive. Design tokens are resolved by the mapping layer; the
backend does not hard-code colors or dimensions from literals when tokens are required.

The first implementation covers only constructs with an unambiguous native equivalent, including `.padding`,
`.frame`, `.background`, `.foregroundColor`, `.font`, `.fontWeight`, `.cornerRadius`, `.opacity`, alignment and
stack spacing. Unsupported cases fail instead of dropping an attribute. Mapping is a compile-time operation; no
runtime modifier registry or generic object bag is introduced.

## Stable-key lists

`List` is the only lazy-list owner in the v0 backend. A dynamic row collection is a typed model property that
implements ArkUI's `IDataSource` in the consuming app; it is not a plain Swift `Array` copied into a generated
adapter. `LazyForEach` receives that data source directly and its `keyGenerator` returns the subset's stable stored
identity. Each datum becomes one `ListItem`; item content preserves the source order and item modifiers. Keys are
strings in ArkUI, so the IR carries a typed key expression and an explicit conversion for an `Int` identity; array
indices are not keys. This decision follows the shared subset/model contract and avoids a second, independently
synchronized source of truth.

```ts
@ComponentV2
export struct SettingsList {
  @Require @Param model: SettingsListModel;

  build() {
    List() {
      LazyForEach(this.model.items, (item: SettingItem) => {
        ListItem() {
          Text(item.title)
        }
      }, (item: SettingItem): string => item.id)
    }
  }
}
```

This is a shape specification, not evidence that it compiles; the toolchain check is listed below. `SettingsListModel`
exposes `items: IDataSource`, whose `getData` returns `SettingItem`. The app owns that implementation and its native
listener notifications, with `@ObservedV2`/`@Trace` for observable item properties. The generator does not invent an
observer registry or add a Refract runtime.

Official `@Monitor` documentation states that watching an entire array does not observe replacement of an item or
Array API mutations. Therefore a generated data-source copy synchronized by `@Monitor` is not a correct general list
contract. Direct `IDataSource` ownership makes update delivery explicit and keeps stable keys across native list
updates. The shared model frontend supplies the item type and identity; the backend never guesses `SettingItem` from
a property named `items` and never silently uses an untyped `Item` fallback.

## Native modal hosts

A bounded sheet attaches `.bindSheet` to the generated root's real modifier chain, with one named `@Builder` for
content and a native `onWillDismiss` that completes `DismissSheetAction.dismiss()` before synchronizing the declared
Boolean owner. It never substitutes a conditional `Column` for the platform's modal host.

`AlertDialog.show` is an imperative UIContext operation, not a builder attribute. The generator does not call it from
`build()`. A typed `@Event on<State>Present` fires from `aboutToAppear` when initially presented and from `@Monitor`
when its declared Boolean becomes true; the application's native component handles that event with
`getUIContext().showAlertDialog`, localized title/message/buttons and matching dismissal writes. This is native
integration without a controller registry, custom overlay host or imperative view-builder side effect. The complete
source and verification boundary are in `docs/navigation.md`; these API 12+ shapes have not been compiler-verified.

## Formatting and diagnostics

The backend uses an indentation-aware writer, never global regular-expression formatting. Strings and identifiers
are escaped using one shared implementation. Stable generated type names include the component and, when needed, a
stable occurrence index; they do not depend on hash iteration order or absolute paths.

Backend-unsupported IR produces a stable-coded error at the originating source location. Expected `.ets` fixtures
are reviewed as hand-written native code, and all golden outputs are inspected after regeneration. No expected output
is generated from a failed or partial lowering.

## Typed optional and payload branches

Immutable optional scalar screen inputs use `T | null | undefined` and an explicit `if let ... else` source form.
The ArkUI builder checks both null and undefined, then creates a local immutable scalar alias. Optional model, state
and binding inputs remain unsupported until their observation semantics are defined separately.

A payload enum is limited to one unlabeled scalar payload on every declared case. The generated representation is a
union of final classes, each with a readonly typed payload field and explicit constructor; branches use `instanceof`
and a local `const` value. Mixed/no-payload cases, object graphs, reference casts and ambiguous patterns are rejected.
Official ArkTS `@Param` documentation supports null, undefined and union types, and the language introduction shows
`instanceof` narrowing on class unions:

- https://gitee.com/openharmony/docs/blob/master/zh-cn/application-dev/ui/state-management/arkts-new-param.md
- https://gitee.com/openharmony/docs/blob/master/zh-cn/application-dev/quick-start/introduction-to-arkts.md
- https://gitee.com/openharmony/docs/blob/master/zh-cn/application-dev/quick-start/typescript-to-arkts-migration-guide.md

These references establish the documented syntax and decorator constraints only. They are not compiler evidence.

## Toolchain verification

No HarmonyOS SDK or DevEco command-line compiler was found in the investigated local environments. Read-only review
of a separate application's `devecocli` workflow found the application and `entry@ohosTest` command pattern, but no
compiler or native build output; that is source evidence only. Public documentation pages were reachable as web
application shells, not compiler artifacts. An unauthenticated, license-compatible Linux SDK and build-tool
distribution has not been established. `docs/harmony-toolchain.md` records the precise authorization blocker and
post-acquisition commands; no account was created or terms accepted on a user's behalf. Until an authorized compiler
runs, `swift build`, `swift test`, golden diffs and the prepared native test target verify preparation or generation,
not ArkTS compilation. Simulator or emulator results, if later available, will be labelled and never presented as
device performance results.

## Current scope and dependencies

The shared IR and golden runner are supplied by #1, the normative Swift subset by #2, model observation by #5,
design-system resolution by #6, native references by #7 and resources by #8. This backend implements their typed IR
representations rather than introducing a second mapping or view tree. Design-system calls are accepted only after
their target names, parameter order and types are resolved by the mapping layer.
